# 登录状态 Cleanup

[← 返回总览](./README.md)

Cleanup 是二维码成绩更新的安全门槛。本文件只描述可验证的行为和公开状态，不描述恢复记录格式、存储实现、加密方案或 worker 源码。

## 1. 安全目标

- 正常完成、业务失败、超时、进程退出和意外中断都必须进入安全收尾。
- 在进入可能产生临时登录状态的阶段前，worker 必须确认恢复能力可用；否则应提前失败。
- worker 重启后必须能够发现尚未结束的状态并优先清理。
- 清理成功前不得写入本次成绩。
- 清理成功前，同一用户不得创建新的二维码成绩任务。
- 恢复流程不得继续旧任务的成绩读取，也不得把旧二维码用于新任务。

## 2. 公开状态

| cleanupStatus | Backend / Frontend 行为 |
| --- | --- |
| not_required | 尚无清理义务；按普通任务状态处理 |
| pending | 继续轮询，禁止新建二维码任务 |
| succeeded | 可以进入成绩持久化或结束失败任务 |
| unconfirmed | 显示安全提示，按 retryAfter 阻止新任务并告警 |

cleanupStatus 与业务 status 独立。业务失败后，cleanup 仍可能继续运行。

## 3. 状态约束

允许的高层变化为：

    not_required -> pending -> succeeded
                            -> unconfirmed
    unconfirmed -> pending -> succeeded

- succeeded 是单向终态，不能回退。
- unconfirmed 表示系统暂时无法证明临时状态已经结束，不表示可以忽略。
- 后续恢复成功时，可以把 unconfirmed 推进到 succeeded。
- 已中断任务即使完成清理，也应保持业务失败，并要求用户使用新二维码重试。

## 4. 中断恢复

worker 必须维护受保护、短时且最小化的恢复信息，以便在中断后完成安全收尾。

恢复机制应满足：

- 只保存完成清理所必需的信息；
- 不保存二维码、成绩快照或可用于继续业务读取的信息；
- 多实例同时发现同一任务时，最多一个实例拥有有效清理权；
- 旧实例恢复运行后不能覆盖新 owner 的清理结果；
- 恢复记录损坏或不可用时 fail closed，并产生可操作告警；
- 清理确认后及时删除或失效恢复信息。

具体存储、并发控制和保护机制属于 worker 私有实现。

## 5. 无法确认的窗口

外部交互可能出现“请求结果未知”的情况。系统无法证明是否产生临时登录状态时：

1. 不得盲目重复相关操作。
2. 不得写入成绩。
3. 将 cleanupStatus 置为 unconfirmed。
4. 返回安全的 retryAfter。
5. 记录告警，等待自动恢复、自然失效或管理员确认。

用户错误文案不得暴露机台侧响应或内部恢复信息。

## 6. 优雅退出

收到正常退出信号后，worker 应：

1. 停止领取新任务。
2. 让未进入敏感阶段的任务安全退出。
3. 优先完成活动任务的收尾。
4. 等待必要的状态与日志提交。
5. 在部署允许的退出窗口内结束进程。

如退出窗口内仍无法确认清理，任务必须保留为 pending 或 unconfirmed，交由恢复流程处理，不能伪造成功。

## 7. Backend 约束

- finalizer 只接受 cleanupStatus 为 succeeded 的成功结果。
- 通用任务失败、队列修复或超时逻辑不得覆盖未完成的 cleanup 状态。
- 活动任务查询必须包含 pending 和仍在阻塞期内的 unconfirmed 任务。
- 用户响应只返回 cleanupStatus、脱敏错误和可选 retryAfter。
- Admin 可以查看数量、时长和错误分类，但不能查看恢复记录内容。
